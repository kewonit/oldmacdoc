# macOS System Integration for a Third-Party Dock Replacement (Swift/AppKit, macOS 14 to 27, Developer ID, not sandboxed)

Primary reference implementation: **Docky** (josejuanqm/docky, GPLv3, macOS 14+, Swift). It hides the system Dock, runs a non-activating dock panel, tracks running apps and shows a Trash tile. I read its source at commit `cb7a6a6` (Oct 27, 2026), so it reflects current macOS. Secondary reference: **DockDoor** (ejbills/DockDoor) at commit `3044142` (Oct 26, 2026). I verified API names against the local macOS SDK headers on a Darwin 27 machine with current Xcode.

Abbreviations: DOCKY = `https://github.com/josejuanqm/docky/blob/cb7a6a64483b5cef82b308b6a0958d0df839a779`; DOCKDOOR = `https://github.com/ejbills/DockDoor/blob/3044142c907b9cdd49917628847a04970450a8e6`. Each link below is written out in full.

## 1. Hiding Apple's Dock (defaults keys, Dock restart, save/restore, crash recovery)

### Takeaway
Use the approach Docky ships today. Snapshot `com.apple.dock` keys `autohide`, `autohide-delay`, `autohide-time-modifier`, `no-bouncing`, `launchanim` and `orientation`. Write `autohide=true`, `autohide-delay=1000.0`, `autohide-time-modifier=0.0`, `no-bouncing=true`, `launchanim=false` through `CFPreferencesSetAppValue` plus `CFPreferencesAppSynchronize`. Then restart the Dock: force-terminate `com.apple.dock`, or run `/usr/bin/killall Dock`. A Dock restart is required. Crash safety takes two layers: (a) a state plist that records the owner PID, checked on next launch, and (b) a tiny bundled watchdog helper app that polls the owner PID and restores the settings if the dock app dies.

### Cited Findings
- Docky's exact hidden values: `"autohide": true`, `"autohide-delay": 1000.0`, `"autohide-time-modifier": 0.0`, `"no-bouncing": true`, `"launchanim": false`. The managed (snapshotted) key list also includes `"orientation"`. — [Docky SystemDockVisibilityService.swift](https://github.com/josejuanqm/docky/blob/cb7a6a64483b5cef82b308b6a0958d0df839a779/Docky/Services/SystemDockVisibilityService.swift)
- How Docky writes the values: `CFPreferencesSetAppValue(key as CFString, value, "com.apple.dock" as CFString)` for each key, then `CFPreferencesAppSynchronize(dockDomain)`. It reads with `CFPreferencesCopyAppValue`. It does not shell out to `/usr/bin/defaults`. — [Docky SystemDockVisibilityService.swift](https://github.com/josejuanqm/docky/blob/cb7a6a64483b5cef82b308b6a0958d0df839a779/Docky/Services/SystemDockVisibilityService.swift)
- How Docky restarts the Dock: from the main app, `NSRunningApplication.runningApplications(withBundleIdentifier: "com.apple.dock").forEach { $0.forceTerminate() }`. From the watchdog, `Process` runs `/usr/bin/killall` with args `["Dock"]`. — [Docky SystemDockVisibilityService.swift](https://github.com/josejuanqm/docky/blob/cb7a6a64483b5cef82b308b6a0958d0df839a779/Docky/Services/SystemDockVisibilityService.swift); [Docky DockyDockWatchdog/main.swift](https://github.com/josejuanqm/docky/blob/cb7a6a64483b5cef82b308b6a0958d0df839a779/DockyDockWatchdog/main.swift)
- Snapshot format: each managed key's current value is stored. If a key was unset, a sentinel string `"__docky_null__"` is stored instead, so restore calls `CFPreferencesSetAppValue(key, nil, domain)` and deletes the key rather than writing a guessed default. The snapshot lives in the app's own `UserDefaults` under `docky.systemDockVisibilitySnapshot`, and a copy sits in `~/Library/Application Support/Docky/SystemDockVisibilityState.plist` with fields `active`, `ownerPID`, `sessionID` (a UUID) and `snapshot`. The plist is written atomically. — [Docky SystemDockVisibilityService.swift](https://github.com/josejuanqm/docky/blob/cb7a6a64483b5cef82b308b6a0958d0df839a779/Docky/Services/SystemDockVisibilityService.swift)
- Hide sequence: `snapshot = existingSnapshot ?? captureSnapshot()` (never re-snapshot while already hidden), then `writeActiveState`, `startWatchdogIfNeeded`, `applyHiddenValues`, `restartDock`. — [Docky SystemDockVisibilityService.swift](https://github.com/josejuanqm/docky/blob/cb7a6a64483b5cef82b308b6a0958d0df839a779/Docky/Services/SystemDockVisibilityService.swift)
- Next-launch crash recovery: `recoverStaleSnapshotIfNeeded()` restores if the state file says `active == true` and the owner PID is no longer running, or if a leftover snapshot exists while the file is inactive. — [Docky SystemDockVisibilityService.swift](https://github.com/josejuanqm/docky/blob/cb7a6a64483b5cef82b308b6a0958d0df839a779/Docky/Services/SystemDockVisibilityService.swift)
- Watchdog design: a separate helper `DockyDockWatchdog.app` is embedded at `Contents/Library/LoginItems/` and code-signed on copy. It is launched with `NSWorkspace.shared.openApplication(at:configuration:)`, `configuration.activates = false` and `configuration.arguments = [statePlistPath, ownerPID, sessionID, bundleID]`. It loops while the state matches, using `kill(pid, 0) == 0 || errno == EPERM` as the liveness test, with `Thread.sleep(0.5)`. When the owner dies and the state is still active for the same session, it restores the snapshot, clears the snapshot key in the main app's domain, runs `killall Dock` and deletes the state file. A clean quit or unhide clears the state file, so the watchdog exits without doing anything. — [Docky DockyDockWatchdog/main.swift](https://github.com/josejuanqm/docky/blob/cb7a6a64483b5cef82b308b6a0958d0df839a779/DockyDockWatchdog/main.swift); [Docky SystemDockVisibilityService.swift](https://github.com/josejuanqm/docky/blob/cb7a6a64483b5cef82b308b6a0958d0df839a779/Docky/Services/SystemDockVisibilityService.swift)
- Shell equivalent from the community: `defaults write com.apple.dock autohide-delay -float 9999999; killall Dock`, or `-float 999`. To revert: `defaults delete com.apple.dock autohide-delay; killall Dock`. The Dock is delayed, not removed, so it can still appear after a long hover. — [MacRumors thread](https://forums.macrumors.com/threads/hide-dock.1569696); [Apple Community](https://discussions-jp-prz.apple.com/thread/254739378)
- Private-API alternative (DockDoor): `@_silgen_name("CoreDockSetAutoHideEnabled") func CoreDockSetAutoHideEnabled(_ flag: Bool)` and `CoreDockGetAutoHideEnabled() -> Bool`. Its `DockAutoHideManager` saves `wasAutoHideEnabled` and restores it later. This only toggles autohide; it does not set the delay. — [DockDoor PrivateApis.swift](https://github.com/ejbills/DockDoor/blob/3044142c907b9cdd49917628847a04970450a8e6/DockDoor/Utilities/PrivateApis.swift); [DockDoor DockUtils.swift](https://github.com/ejbills/DockDoor/blob/3044142c907b9cdd49917628847a04970450a8e6/DockDoor/Utilities/DockUtils.swift)
- Other open-source projects: DockMaster Pro advertises a "Hide macOS Dock" feature that restores the original Dock settings on quit. Its canonical repository is unclear (the build docs point to `qianmoQ/DockMaster`, which returned "Repository not found" when I tried to clone it). — [DockMaster Pro mirror](https://proxy-ga.blitzz.co/proxy/123456/github.com/devlive-community/DockMaster-Pro)
- macOS 26 report: one Apple Community user said the Dock disappeared randomly on macOS Tahoe 26.0 and that 26.1 fixed it. This is anecdotal. — [Apple Community (Tahoe dock disappears)](https://discussions-cn-prz.apple.com/en/thread/256138247?page=3)

### Inferences
- Docky's last commit is dated Oct 27, 2026, it targets macOS 14+, and it still uses these exact keys with a Dock restart. That strongly suggests the approach still works on macOS 26 Tahoe and 27. I found no Apple statement either way.
- `CFPreferences*` for another app's domain works from a non-sandboxed, hardened-runtime app (Docky ships this way). It is better than editing `~/Library/Preferences/com.apple.dock.plist` directly, because cfprefsd caches values. Shelling out to `/usr/bin/defaults` also works but adds nothing.
- Snapshotting `orientation` lets the app move the hidden system Dock to a different screen edge, so its reveal zone does not collide with the replacement dock's own edge trigger. Docky exposes `setOrientation`.
- A LaunchAgent watchdog is an alternative, but Docky's helper-app approach (launched per session, keyed by PID and session) avoids installing anything persistent and needs no `SMAppService.agent` registration.
- Also restore in `applicationWillTerminate` and on logout or shutdown (`NSWorkspace.willPowerOffNotification`). SIGKILL and crashes are covered by the watchdog plus the next-launch check.

### Gaps
- I found no documentation of how the commercial apps (uBar, ActiveDock, LegacyDock) hide the Dock. I did not search further because of the budget.
- I found no Apple documentation of `no-bouncing` or `launchanim` and no macOS 26/27 changelog for Dock preference keys.
- I did not find whether `CoreDockSetAutoHideEnabled` still links on macOS 27. DockDoor's current main uses it, so it probably still works.

## 2. Dock window (NSPanel config, level, Spaces and full screen, auto-hide)

### Takeaway
Use an `NSPanel` subclass with `.nonactivatingPanel`. Return `canBecomeKey = false` and `canBecomeMain = false`, use a clear non-opaque background, and set collectionBehavior `[.canJoinAllSpaces, .stationary, .ignoresCycle]`, adding `.fullScreenAuxiliary` only if you want the dock to appear over full-screen apps. Set the app to `.accessory` activation policy. Docky pins the level to `.mainMenu` (24); Apple's Dock uses `kCGDockWindowLevel` (20). Detect full screen with `CGWindowListCopyWindowInfo` and re-check on space or activation changes. For auto-hide reveal, a global `.mouseMoved` monitor does not need Accessibility according to Apple's docs (only key events do), but pair it with a local monitor.

### Cited Findings
- Docky's main dock window is `final class MainWindow: NSPanel`. The comment explains: "NSPanel (not NSWindow) so the `.nonactivatingPanel` style mask actually takes effect, that's the only way to keep clicks on the dock from activating Docky as a foreground app". The init forces `styleMask: style.union(.nonactivatingPanel)`. — [Docky MainWindow.swift](https://github.com/josejuanqm/docky/blob/cb7a6a64483b5cef82b308b6a0958d0df839a779/Docky/Views/MainWindow/MainWindow.swift)
- Overrides: `canBecomeKey { Self.allowsKeyWindow }`, which defaults to `false` and is flipped to `true` only while an embedded text field has focus. `canBecomeMain { false }`. `override var level: NSWindow.Level { get { .mainMenu } set {} }`. Setup sets `backgroundColor = .clear`, `isOpaque = false`, `isMovableByWindowBackground = false` and `acceptsMouseMovedEvents = true`. Magnification uses an `NSTrackingArea` with `[.activeAlways, .inVisibleRect, .mouseEnteredAndExited, .mouseMoved]`. — [Docky MainWindow.swift](https://github.com/josejuanqm/docky/blob/cb7a6a64483b5cef82b308b6a0958d0df839a779/Docky/Views/MainWindow/MainWindow.swift)
- Collection behaviors in Docky: "all spaces" mode uses `[.canJoinAllSpaces, .stationary, .ignoresCycle]` plus `.fullScreenAuxiliary`. "Active space" mode uses `[.moveToActiveSpace, .stationary, .ignoresCycle]`. — [Docky DockyPreferences.swift](https://github.com/josejuanqm/docky/blob/cb7a6a64483b5cef82b308b6a0958d0df839a779/Docky/Services/DockyPreferences.swift)
- Activation policy: `NSApplication.shared.setActivationPolicy(.accessory)` at launch. Docky switches to `.regular` while its Settings window is open and back to `.accessory` afterwards. — [Docky AppDelegate.swift](https://github.com/josejuanqm/docky/blob/cb7a6a64483b5cef82b308b6a0958d0df839a779/Docky/AppDelegate.swift)
- SDK window level constants (CGWindowLevel.h): `kCGDockWindowLevel = 20`, `kCGMainMenuWindowLevel = 24`, `kCGStatusWindowLevel = 25`; `kCGDockWindowLevelKey` exists. NSWindow.h header notes: `IgnoresCycle` is the "Default behavior if windowLevel != NSNormalWindowLevel"; `Stationary` means "Unaffected by exposé. Stays visible and stationary, like desktop window"; `FullScreenAuxiliary` means "can be shown with the fullscreen window"; new in macOS 13: `.primary`, `.auxiliary`, `.canJoinAllApplications`. — macOS SDK headers (local Xcode, `CGWindowLevel.h`, `NSWindow.h`); see also [Apple NSWindow.CollectionBehavior](https://developer.apple.com/documentation/appkit/nswindow/collectionbehavior-swift.struct)
- Full-screen detection in Docky: `CGWindowListCopyWindowInfo([.optionOnScreenOnly, .excludeDesktopElements], kCGNullWindowID)`. It considers only `kCGWindowLayer == 0` windows not owned by its own PID, flips `kCGWindowBounds` from CG top-left coordinates to NSScreen coordinates (`y = primaryHeight - maxY`), and treats a window as a full-screen candidate if its bounds match the whole `screen.frame` (menu bar included). It then confirms through its Accessibility-backed window registry. It re-evaluates on `NSWorkspace.activeSpaceDidChangeNotification` and on app activation, with delayed re-checks because the space change fires during the full-screen exit animation. It separately detects "maximized" windows that fill `visibleFrame` against the dock's edge. — [Docky MainWindow.swift](https://github.com/josejuanqm/docky/blob/cb7a6a64483b5cef82b308b6a0958d0df839a779/Docky/Views/MainWindow/MainWindow.swift)
- Auto-hide reveal in Docky: "A hidden panel sits off-screen, where its tracking area can't fire, so the reveal runs off monitored pointer movement instead." It installs `NSEvent.addGlobalMonitorForEvents(matching: [.mouseMoved, .leftMouseDragged, .rightMouseDragged, .otherMouseDragged])` plus a matching `addLocalMonitorForEvents`, only while autohide can hide the dock, so it doesn't wake on every system-wide mouse move. It uses `revealTriggerThickness: CGFloat = 2`. Docky installs this reveal monitor without an Accessibility check, but gates a different global pointer monitor (multi-display follow-pointer) on `accessibility == .granted`. — [Docky MainWindow.swift](https://github.com/josejuanqm/docky/blob/cb7a6a64483b5cef82b308b6a0958d0df839a779/Docky/Views/MainWindow/MainWindow.swift)
- Apple's docs on global monitors: "Key-related events may only be monitored if accessibility is enabled or if your application is trusted for accessibility access." Also: "your handler will not be called for events that are sent to your own application", and events are observe-only and cannot be modified. `NSMouseMoved` is in the list of monitorable types. — [Apple: addGlobalMonitorForEvents(matching:handler:)](https://developer.apple.com/documentation/appkit/nsevent/addglobalmonitorforevents(matching:handler:))

### Inferences
- Configuration for v1 with no special permissions: `NSPanel(contentRect:, styleMask: [.borderless, .nonactivatingPanel], backing: .buffered, defer: false)`, `hidesOnDeactivate = false` (panels default to `true`, and an `.accessory` app is almost never active), `isFloatingPanel = true` or an explicit level, `hasShadow` as desired, `canBecomeKey/Main = false`, and `LSUIElement = YES` in Info.plist or `setActivationPolicy(.accessory)`.
- Level choice: `NSWindow.Level(rawValue: Int(CGWindowLevelForKey(.dockWindow)))` (20) matches Apple's Dock. It sits above normal and floating windows and below menus, the menu bar, pop-ups and the screensaver. Docky's `.mainMenu` (24) also works but puts the dock in the same band as the menu bar.
- To hide in other apps' full-screen Spaces, omit `.fullScreenAuxiliary`; the panel then does not appear in full-screen Spaces. Use the CGWindowList heuristic only if you also want to hide over "maximized" windows. Window bounds, layer and owner PID from `CGWindowListCopyWindowInfo` are generally available without Screen Recording (titles are not), but I did not verify this with a primary source.
- Instead of a global monitor, or as a fallback, you can keep a 2-pt-tall transparent panel at the screen edge with an `.activeAlways` tracking area (`ignoresMouseEvents = false`). This avoids any concern about global monitors and wakes only when the pointer reaches the edge.

### Gaps
- I found no explicit Apple statement for macOS 26/27 confirming that global `.mouseMoved` monitors still work without Accessibility. The docs restrict only key events. Docky's mixed gating suggests either developer caution or behavior seen in one scenario. Test this on 26/27.
- I found nothing on Tahoe-specific changes to NSPanel levels or full-screen Space behavior for third-party docks.

## 3. Running apps, activation, launching and quitting

### Takeaway
List apps with `NSWorkspace.shared.runningApplications.filter { $0.activationPolicy == .regular }`, excluding yourself. Observe didLaunch, didTerminate, didHide, didUnhide and didActivate on `NSWorkspace.shared.notificationCenter`, and re-check later, because some apps become `.regular` after launch. For apps that aren't running, use `openApplication(at:configuration:)` with `activates = true`. For running apps, call `unhide()` and then `activate(from: NSWorkspace.shared.frontmostApplication ?? .current, options:)` (macOS 14+), falling back to `activate(options:)`. `ignoringOtherApps` has no effect from macOS 14 on. An `.accessory` dock app can activate other apps; a `.regular` app that isn't frontmost cannot.

### Cited Findings
- Docky's filter: `NSWorkspace.shared.runningApplications.filter { $0.activationPolicy == .regular && $0.bundleIdentifier != dockyBundleID }`. It matches by bundle ID so debug builds launched from Xcode are also excluded. — [Docky WorkspaceService.swift](https://github.com/josejuanqm/docky/blob/cb7a6a64483b5cef82b308b6a0958d0df839a779/Docky/Services/WorkspaceService.swift)
- Observed notifications: `NSWorkspace.didLaunchApplicationNotification`, `didTerminateApplicationNotification`, `didHideApplicationNotification`, `didUnhideApplicationNotification` and `didActivateApplicationNotification`. Gotcha: "some apps launch as `.prohibited` or `.accessory` and only become dock-eligible once their first window appears", so Docky re-runs its refresh on later window changes as well as on `didLaunch`. — [Docky WorkspaceService.swift](https://github.com/josejuanqm/docky/blob/cb7a6a64483b5cef82b308b6a0958d0df839a779/Docky/Services/WorkspaceService.swift)
- SDK: `NSApplicationActivateIgnoringOtherApps` is `API_DEPRECATED("ignoringOtherApps is deprecated in macOS 14 and will have no effect.", macos(10.6, 14.0))`. `-activateFromApplication:options:` is `API_AVAILABLE(macos(14.0)) NS_SWIFT_NAME(activate(from:options:))`. `-activateWithOptions:` is still present. — macOS SDK header `NSRunningApplication.h` (local Xcode)
- Apple's article on cooperative activation (macOS 14): "Cooperative activation addresses this problem by making app activation a request instead of a command." "Only the active app can influence the activation context. It does so by yielding to an explicit target app before the target app activates." "NSWorkspace automatically handles this for you when opening URLs or applications." Pattern: `NSApp.yieldActivation(to: targetApp); targetApp.activate()`. — [Apple: Passing control from one app to another with cooperative activation](https://developer.apple.com/documentation/appkit/passing-control-from-one-app-to-another-with-cooperative-activation)
- `activate(from:options:)`: the return value only says whether the system permits the request, and activation is not guaranteed. — [Apple: NSRunningApplication.activate(from:options:)](https://developer.apple.com/tutorials/data/documentation/appkit/nsrunningapplication/activate(from:options:).md)
- Docky's real-world finding (AppActivation.swift comment): "Since macOS 14 activation is cooperative: `NSRunningApplication.activate` is honored only when the requesting process is allowed to hand over activation. A `.regular` app that isn't itself frontmost is not, so the call returns false and nothing happens. Docky normally runs `.accessory`, which the system exempts." While Docky was temporarily `.regular` (Settings open), every tile click failed (issue #35). The fix is `activate(from: NSWorkspace.shared.frontmostApplication ?? .current, options:)` with a fallback to `activate(options:)`. — [Docky AppActivation.swift](https://github.com/josejuanqm/docky/blob/cb7a6a64483b5cef82b308b6a0958d0df839a779/Docky/Services/AppActivation.swift)
- Docky's click flow (`activateOrOpen`): if the app isn't running, it uses `NSWorkspace.shared.urlForApplication(withBundleIdentifier:)` and then `openApplication(at:configuration:)` with `configuration.activates = true`. If the app is running and has windows on another Space, it calls `unhide()` and then `activateTransferringFrontmost(options: [.activateAllWindows])`. If the app is running with no windows, it calls `openApplication(at:)` again, which relies on Launch Services' reopen behavior. Window enumeration and minimize-restore use Accessibility (`AXUIElementSetAttributeValue(..., kAXMinimizedAttribute, kCFBooleanFalse)`), and per-window focus also uses private SkyLight. — [Docky WorkspaceService.swift](https://github.com/josejuanqm/docky/blob/cb7a6a64483b5cef82b308b6a0958d0df839a779/Docky/Services/WorkspaceService.swift); [Docky WindowRegistry.swift](https://github.com/josejuanqm/docky/blob/cb7a6a64483b5cef82b308b6a0958d0df839a779/Docky/Services/WindowRegistry.swift)
- `NSWorkspace.OpenConfiguration` properties: `activates`, `addsToRecentItems`, `allowsRunningApplicationSubstitution`, `createsNewApplicationInstance`, `hides`, `hidesOthers`, `promptsUserIfNeeded`, `appleEvent`, `arguments`, `environment`, `architecture`, `requiresUniversalLinks`, `isForPrinting`. — [Apple: NSWorkspace.OpenConfiguration](https://developer.apple.com/documentation/appkit/nsworkspace/openconfiguration)
- Docky's README: Docky needs Accessibility and Screen Recording "to manage windows and render previews". It uses private SkyLight/CGS and Accessibility SPI and therefore "cannot be distributed on the Mac App Store". — [Docky README](https://github.com/josejuanqm/docky/blob/cb7a6a64483b5cef82b308b6a0958d0df839a779/README.md)
- Wine's macOS 14 adoption notes say yields must be issued in response to another app trying to activate, not preemptively. — [WineHQ MR thread](https://list.winehq.org/hyperkitty/list/wine-gitlab@list.winehq.org/thread/K4XSASJC5FYH262CAN453KE4ZHNRCKDX/)

### Inferences
- For a v1 click handler with no special permissions: if the app isn't running, call `openApplication(at:configuration:)` with `activates = true`. If it is running, call `openApplication(at: app.bundleURL!, configuration:)` again. Launch Services treats this like a Finder double-click, which typically triggers the app's reopen handler and so creates a window or restores minimized windows for most apps. Opening through NSWorkspace also gets cooperative-activation handling automatically, per Apple. Use `unhide()` plus `activate(from:options:)` when you only need to bring a hidden app forward without the reopen side effects.
- Keep the dock app `.accessory` at all times. If you show a Settings window, see Docky's issue #35 pitfall above and always use `activate(from:)`.
- To quit, use `NSRunningApplication.terminate()` (polite, and the app may show save prompts). `forceTerminate()` exists, and Docky uses it on the Dock process. Neither needs a TCC permission. Unlike sending Apple Events, `NSRunningApplication` methods don't need an Automation permission prompt.
- `NSWorkspace.runningApplications` is KVO-observable, and `NSRunningApplication.activationPolicy`, `isHidden` and `isActive` are KVO-observable too. KVO on `activationPolicy` is a cleaner fix than re-polling for the "becomes .regular later" case. I did not re-verify this against the current docs.
- Badges, progress bars and the menus of other apps' Dock tiles cannot be read through public API; this is not covered by my sources.

### Gaps
- I found no primary Apple statement that `openApplication(at:)` on an already-running app sends `kAEReopenApplication` ('rapp'). Docky's code relies on this behavior, but test it.
- Restoring minimized windows without Accessibility is not possible through public API apart from the reopen event, which only some apps implement that way.

## 4. Trash (location, empty/full state, permissions, drop-to-trash, icons)

### Takeaway
Listing `~/.Trash` is TCC-protected: without Full Disk Access you get "Operation not permitted", even as root. Docky's TrashService reads `~/.Trash` directly with no FDA handling, so without FDA it silently shows "empty". Moving files to the Trash with `FileManager.trashItem(at:resultingItemURL:)` or `NSWorkspace.recycle(_:)` works without FDA. Icons: `NSImage(named: NSImage.trashEmptyName)` and `NSImage(named: NSImage.trashFullName)`.

### Cited Findings
- "Operation not permitted" on `~/.Trash` means system privacy policy is blocking the app, not Unix permissions. `sudo ls -lah ~/.Trash` also fails. The fix is Full Disk Access for the calling process. — [Apple Developer Forums 122716](https://developer.apple.com/forums/thread/122716) (user answer, not Apple staff)
- On Sonoma, a cron job could not read `~/.Trash` even with FDA granted to cron and Terminal. Apple DTS suggested testing other FDA-protected directories, and the thread was unresolved. — [Apple Developer Forums 745692](https://developer.apple.com/forums/thread/745692)
- The maclean tool treats a Trash read error as an FDA problem ("macOS hides Trash from apps without FDA; sudo won't help"). — [maclean trash.rs](https://docs.rs/crate/maclean/latest/source/src/modules/trash.rs)
- A Jamf user fixed Trash access by granting FDA to the host app. — [Jamf Community](https://community.jamf.com/general-discussions-2/need-a-script-to-delete-files-after-x-number-days-in-the-trash-20779)
- Docky TrashService: `homeDirectoryForCurrentUser.appendingPathComponent(".Trash")`, `contentsOfDirectory(at:includingPropertiesForKeys: nil, options: [.skipsHiddenFiles])`, `isEmpty = contents?.isEmpty != false` (so a failed read counts as empty), and a watcher `open(path, O_EVTONLY)` plus `DispatchSource.makeFileSystemObjectSource(fileDescriptor:, eventMask: [.write, .rename, .delete], queue: .main)`. Docky's README asks only for Accessibility and Screen Recording, not FDA. — [Docky TrashService.swift](https://github.com/josejuanqm/docky/blob/cb7a6a64483b5cef82b308b6a0958d0df839a779/Docky/Services/TrashService.swift); [Docky README](https://github.com/josejuanqm/docky/blob/cb7a6a64483b5cef82b308b6a0958d0df839a779/README.md)
- Docky's drop-to-trash: `for url in urls where (try? FileManager.default.trashItem(at: url, resultingItemURL: nil)) != nil`. — [Docky MainWindowView.swift](https://github.com/josejuanqm/docky/blob/cb7a6a64483b5cef82b308b6a0958d0df839a779/Docky/Views/MainWindow/MainWindowView.swift)
- SDK: `NSImageNameTrashEmpty` and `NSImageNameTrashFull` (macOS 10.6+; Swift `NSImage.trashEmptyName` / `NSImage.trashFullName`). `-[NSWorkspace recycleURLs:completionHandler:]` "moves the given files to the trash ... in the same manner as the Finder" (Swift `NSWorkspace.shared.recycle(_:completionHandler:)`). Docky loads its trash icons with `NSImage(named:)`. — macOS SDK headers `NSImage.h` and `NSWorkspace.h` (local Xcode); [Docky TrashTileView.swift](https://github.com/josejuanqm/docky/blob/cb7a6a64483b5cef82b308b6a0958d0df839a779/Docky/Views/Tiles/TrashTileView.swift)

### Inferences
- Use `FileManager.default.url(for: .trashDirectory, in: .userDomainMask, appropriateFor: nil, create: false)` to get the Trash location instead of hard-coding `~/.Trash`. Other volumes keep their own trash folders (`/Volumes/X/.Trashes/<uid>`), so per-user "full" detection is never complete through the file system alone.
- Options for empty/full state, from fewest to most permissions:
  - (a) Show only the empty icon until a drop happens, then show full; the state can be wrong.
  - (b) Ask for Full Disk Access (optional, with a deep link to System Settings > Privacy & Security > Full Disk Access) and read `~/.Trash` when it is granted. Check whether `contentsOfDirectory` throws so a permission failure is not reported as "empty".
  - (c) Ask Finder over Apple Events (`tell application "Finder" to count items of trash`). This needs the Automation TCC prompt, `NSAppleEventsUsageDescription` in Info.plist, and the `com.apple.security.automation.apple-events` entitlement under the hardened runtime.

  Option (b) is the most common approach among utilities.
- To open the Trash in Finder, `NSWorkspace.shared.open(trashURL)` works. Emptying the Trash has no public non-Finder API apart from deleting the contents, which needs FDA; the usual route is Finder Apple Events (`empty trash`), which needs Automation.

### Gaps
- I did not verify whether `open(~/.Trash, O_EVTONLY)` (for the DispatchSource watcher) or `stat`/`resourceValues` on the `.Trash` directory itself succeed without FDA on macOS 14 to 27. If they do, watching the directory's modification date would give a no-permission change signal. This needs testing.
- I found no Apple primary documentation listing `~/.Trash` among TCC-protected locations. The evidence is forum and tool consensus.

## 5. Show in Finder, Keep in Dock / reorder, Launch at login

### Takeaway
"Show in Finder" is `NSWorkspace.shared.activateFileViewerSelecting([url])`, with the URL coming from `urlForApplication(withBundleIdentifier:)`. Keep-in-Dock and drag reordering are your own persisted state, with no system API involved. For launch at login, use `SMAppService.mainApp.register()` / `.unregister()`, checking `.status` first. None of these needs TCC.

### Cited Findings
- `revealApplicationInFinder`: `NSWorkspace.shared.urlForApplication(withBundleIdentifier:)`, then `NSWorkspace.shared.activateFileViewerSelecting([appURL])`. — [Docky WorkspaceService.swift](https://github.com/josejuanqm/docky/blob/cb7a6a64483b5cef82b308b6a0958d0df839a779/Docky/Services/WorkspaceService.swift)
- SDK: `-activateFileViewerSelectingURLs:` (macOS 10.6+). `launchApplication:` is deprecated in favor of `openApplicationAtURL:configuration:completionHandler:`. — macOS SDK header `NSWorkspace.h` (local Xcode)
- Docky LaunchAtLoginService: `switch SMAppService.mainApp.status`, then `if status != .enabled { try SMAppService.mainApp.register() }`, or `else if status != .notRegistered { try SMAppService.mainApp.unregister() }`. — [Docky LaunchAtLoginService.swift](https://github.com/josejuanqm/docky/blob/cb7a6a64483b5cef82b308b6a0958d0df839a779/Docky/Services/LaunchAtLoginService.swift)
- Distribution: Docky ships through direct download, Homebrew cask and Sparkle updates, not the Mac App Store. — [Docky README](https://github.com/josejuanqm/docky/blob/cb7a6a64483b5cef82b308b6a0958d0df839a779/README.md)

### Inferences
- Store pinned items by bundle identifier plus a bookmark or URL fallback. Resolve them with `NSWorkspace.shared.urlForApplication(withBundleIdentifier:)` at launch so moved or updated apps still resolve. Get icons with `NSWorkspace.shared.icon(forFile:)`.
- `SMAppService.mainApp.register()` may leave the status at `.requiresApproval` if the user has disabled it in System Settings > General > Login Items. Show `SMAppService.openSystemSettingsLoginItems()` in that case.
- Under the hardened runtime and outside the sandbox, the v1 feature set (hide Dock through CFPreferences, an `.accessory` NSPanel dock, running-app list, activation, launch, quit, trash drop, Show in Finder, login item) needs no entitlements beyond the defaults and no TCC permissions. The only exception is the Trash full/empty indicator, which needs FDA or Automation.

### Gaps
- I did not find official macOS 26 "Tahoe" or 27 release notes covering SMAppService, NSWorkspace activation or NSPanel. I found no evidence of changes after macOS 14's cooperative activation, and the macOS 27 SDK headers still carry the same deprecation text.
