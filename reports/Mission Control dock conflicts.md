# Yield Mission Control to Apple's Dock

Apple's Dock cannot be kept parked through Mission Control. With `autohide=1`, `autohide-delay=100000` and `no-bouncing=1` it still appears across the bottom of the screen in Mission Control on macOS 27.0.1 and 15.6.1, and in App Exposé, because the Dock's own code carries an "In expose mode; did NOT hide" override and macOS 27's WindowManager has a dedicated `MissionControlDockHoist` that no delay value, `com.apple.dock` key or public API reaches; the one product that suppresses it, DockDoor Pro, does so on macOS 27 alone through a private SkyLight helper. The robust design is to cede these modes rather than fight them: give the dock panel `.transient` collection behaviour so the system removes it in Mission Control and App Exposé and orders it back 15–42 ms into the exit, then fade it yourself within roughly 20–40 ms of entry using a permission-free classifier that spots WindowManager's screen-sized level-19 shield in `CGWindowListCopyWindowInfo` at 0.17–0.6 ms per read. Window level plays no part, since on-device `.stationary` panels stayed above Mission Control at every level from 0 to 1000 and `.transient` panels vanished at every level, which is exactly why a `.stationary` dock produced the "two docks" picture. Detection has narrowed on macOS 27, where no distributed, Darwin or NSWorkspace notification fires and the Dock's `AXExpose*` Accessibility notifications, dependable through macOS 26, never arrive, so the window list (optionally woken by private SkyLight window events) is the only working signal. Auto-hide stays snappy and robust when a fixed window slides a layer for 0.2–0.25 s after a 0.12–0.2 s stillness dwell, goes fully transparent when hidden, arms its triggers only on true display edges, keeps `no-bouncing=1`, and fails toward "visible" whenever a check is uncertain. Show Desktop, Space switches and overlay ownership on macOS 14, 15 and 26 remain untested.

## Apple's Dock ignores a 100,000-second delay whenever Mission Control opens

"On-device" in this report means tests on macOS 27.0.1 (build 26A434), run on a MacBook with an external display stacked above it.

The parked Dock returns in every Mission Control session. On-device, Mission Control showed Apple's current Dock across the bottom while it was parked with `autohide=1`, `autohide-delay=100000` and `no-bouncing=1`, and users see the same thing elsewhere: on macOS 15.6.1 "the system dock is present when accessing Mission Control View… the system dock overlaps the Docky dock" ([Docky #18](https://github.com/josejuanqm/docky/issues/18)), on macOS 27 "the macos dock takes priority over docky dock" ([Docky #90](https://github.com/josejuanqm/docky/issues/90)), and in App Exposé "the native macOS Dock appears again at the bottom of the screen" ([Docky #78](https://github.com/josejuanqm/docky/issues/78)). DockDoor Pro's documentation concedes that before macOS 27 "macOS may still show its own Dock in Mission Control and App Exposé" ([DockDoor Pro llms.txt](https://pro.dockdoor.net/llms.txt)). The delay has no effect because this is not an autohide reveal at all. The macOS 27 Dock binary logs "In expose mode; did NOT hide" and "Override to show", and it hands Mission Control, App Exposé and Show Desktop to WindowManager ("Failed to show all windows via Window Manager"), whose binary in turn contains `MissionControlDockHoist`, `DockRevealComponent` and `minimumDockRevealAmount` (binary strings, macOS 27.0.1). The most consistent reading is that **WindowManager forces a minimum Dock reveal through a show-override that skips the autohide preference entirely**. In the window list, Apple's Dock is a single Dock-owned, display-sized window named `Dock` at layer 20; on-device it came on screen about 45 ms after Mission Control was triggered and left 450–597 ms after the exit began, and no notification marked either moment.

Mission Control is not the only way out. On-device, an app calling `requestUserAttention` made the parked Dock push the bouncing icon up from the edge unless `no-bouncing=1` was set, and a large `autohide-time-modifier` did not stop it, so **`no-bouncing` is a required part of the parking set rather than a cosmetic one**. In a full-screen app on macOS 15.6.1, pushing the pointer to the Dock's edge "always reveals the system dock" whatever the delay ([Docky #18](https://github.com/josejuanqm/docky/issues/18)), which matches separate "Space Forces Hidden" and "Forcing full-screen hidden mode" branches in the Dock's visibility code. The Apps launcher that replaced Launchpad in macOS 26 ([Macworld](https://www.macworld.com/article/2830963/macos-tahoe-apps-replaces-launchpad.html)) did not show Apple's Dock on-device. Two modes are genuinely unknown: no source or test establishes whether the parked Dock reveals during Show Desktop or during a Space switch, and the "spacechange" reason in the Dock's visibility log proves only that it re-evaluates on Space changes, not what it decides.

The app's own panel is governed by a single property. In a 16-panel on-device matrix, `.stationary` panels stayed full-size, unmoved and drawn above the Mission Control shield and window thumbnails, while `.transient` panels (Apple's default for any non-normal level) disappeared, `.managed` panels became thumbnails, and `.auxiliary` panels behaved like `.transient` ([Apple: stationary](https://developer.apple.com/documentation/appkit/nswindow/collectionbehavior-swift.struct/stationary); [Apple: transient](https://developer.apple.com/documentation/appkit/nswindow/collectionbehavior-swift.struct/transient)). The coordinator's test with the real dock panel matched: at `.stationary` both docks were visible in Mission Control, and at `.transient` only Apple's Dock was, with the app's dock returning after exit. Timing shapes what users see, because the system orders hidden windows out only when the entry animation ends, 310–338 ms after the trigger, and orders them back in at the start of the exit, 15–42 ms after it. **A `.transient` dock leaves late and returns early.** Show Desktop removed none of the 16 panels from the on-screen window list, although what they looked like during Show Desktop was not captured.

| Mode (macOS 27.0.1 unless noted) | Apple's parked Dock | App panel, `.stationary` | App panel, `.transient` | WindowManager surfaces present |
|---|---|---|---|---|
| Mission Control | Revealed at bottom (on-device; 15.6.1 per Docky #18) | Stays above shield, so two docks show | Ordered out at 310–338 ms, back 15–42 ms into exit | Level-19 shield per display + level-14 Spaces Bar |
| App Exposé | Revealed (user reports, DockDoor Pro docs) | Stays | Ordered out | Level-19 shield, no Spaces Bar |
| Show Desktop | Unknown | Stays in window list | Stays in window list | Level-18 overlay; none with Stage Manager on |
| Space switch | Unknown | On every Space; motion during the slide untested | Same; untested | None; only Space-change events |
| Apps launcher (26+) | Not shown | Not tested | Not tested | Not measured |
| Attention request | Pushes icon up unless `no-bouncing=1` | Not affected | Not affected | None |
| Full-screen edge push | Revealed despite delay (15.6.1) | Not tested | Not tested | None |

## Only private SPI on macOS 27 keeps Apple's Dock out

There is no supported switch. Apple gives users exactly one Dock-hiding control, "Automatically hide and show the Dock", and its Mission Control settings list no Dock option ([Apple: Desktop & Dock settings, macOS 27](https://support.apple.com/guide/mac-help/change-desktop-dock-settings-mchlp1119/27.0/mac/27.0)). None of the hyphenated preference keys in the macOS 27 Dock binary resembles "show Dock in Mission Control": `mcx-expose-disabled` is a managed-preference switch that appears to turn Mission Control off altogether, and `hidden-is-suppressed` and `dock-visibility` are untested and look like a debug switch and a log category. The Dock cannot be stopped either, because it runs from a SIP-protected launch agent and `killall Dock` simply respawns it ([Docky #47](https://github.com/josejuanqm/docky/issues/47)), and yabai's Dock injection requires partly disabling SIP ([yabai README](https://github.com/koekeishiya/yabai/blob/master/README.md)). The public `NSApplication.PresentationOptions.hideDock` ("The dock is entirely hidden and disabled") applies only "when this app is active" ([Apple: hideDock](https://developer.apple.com/documentation/appkit/nsapplication/presentationoptions-swift.struct/hidedock); [Apple: presentationOptions](https://developer.apple.com/documentation/appkit/nsapplication/presentationoptions-swift.property)), and a non-activating dock is almost never the active app. Docky contains an unshipped probe that sets the Dock's windows to alpha 0 from Docky's own connection, with no recorded result ([Docky SkyLightSpaceReservationProbe.swift](https://github.com/josejuanqm/docky/blob/main/Docky/Private/SkyLightSpaceReservationProbe.swift)).

DockDoor Pro 1.7.3 is the exception, and it words its claim carefully: "Hide Native Dock in Mission Control — Keep the macOS Dock out of Mission Control and App Exposé, on macOS 27 and later" ([DockDoor Pro features](https://pro.dockdoor.net/features/)). Its bundled `DockShield.app` helper, described as "Hides the native Dock during Mission Control", imports `SetSystemUIMode` and loads SkyLight's `SLPSSetFrontProcessWithOptions` and permitted-front-process functions ([DockDoor Pro 1.7.3 DMG](https://downloads.dockdoor.net/v/1.7.3/DockDoorPro.dmg), binary inspection). The likely mechanism, inferred from those imports and not run here, is that the helper briefly becomes the SkyLight front process when Mission Control starts and sets a Dock-hiding system UI mode, landing in the Dock's "In Suppressed UI Mode" branch, which outranks the Mission Control override; doing this from a separate helper spares the main dock app from ever activating. Docky's maintainer, by contrast, says "Unfortunately unless SIP-unlocked this is not possible" ([Docky #78](https://github.com/josejuanqm/docky/issues/78)). Both positions fit the evidence if the suppressed-UI branch only wins once WindowManager hosts Mission Control, which would also explain DockDoor Pro's 27-only gating. The costs are real: the SPI can break in any point release, the front-process swap can redirect App Exposé's target app or keyboard focus, the helper needs a restore path for its own death, and `SetSystemUIMode`'s mode constants are no longer even declared in the macOS 27 SDK headers.

Covering Apple's Dock is no substitute. Docky's dock sits at `.mainMenu` (level 24) with `.stationary`, above the Dock's level 20 ([Docky DockyPreferences.swift](https://github.com/josejuanqm/docky/blob/cb7a6a64483b5cef82b308b6a0958d0df839a779/Docky/Services/DockyPreferences.swift#L471-L483)), yet users still see Apple's Dock overlap it in Mission Control ([Docky #18](https://github.com/josejuanqm/docky/issues/18)); WindowManager's `hoistsDock` and `dockElevationCallbackID` suggest it re-raises the Dock during the transition, and a covered Apple Dock would still take clicks in its band. Two public mitigations shrink the conflict instead. Writing a small `tilesize` and `static-only=1` while parked turns Apple's Mission Control Dock into a strip that "you can see it if you look for it", though Docky's maintainer rejected that default because it weakens App Exposé's per-app switching ([Docky #78](https://github.com/josejuanqm/docky/issues/78)). Parking Apple's Dock on a left or right edge moves its Mission Control reveal clear of a bottom dock; DockDoor Pro ships exactly this ("Pin the system Dock to another edge while it is hidden") ([DockDoor Pro features](https://pro.dockdoor.net/features/)), and a Docky commenter on Tahoe reported that side parking also cured the full-screen-edge reveal ([Docky #18](https://github.com/josejuanqm/docky/issues/18)). The chosen edge must not border another display ([Docky #47](https://github.com/josejuanqm/docky/issues/47)), which the coordinator's stacked arrangement leaves free on both sides. Any extra key the app writes (`tilesize`, `static-only`, `orientation`) has to join the snapshot, the restore-on-quit path and the crash watchdog alongside `autohide`, `autohide-delay`, `autohide-time-modifier`, `no-bouncing` and `launchanim`.

| Policy | Panel behaviour | What the user sees in Mission Control | Requires | Main cost |
|---|---|---|---|---|
| **A. Cede (recommended default)** | `.transient` + early fade | Apple's Dock only | Nothing beyond public APIs | Apple's Dock shows the user's old tiles, not the app's |
| B. Separate edges | `.stationary` + a small `.transient` sentinel | App's dock at the bottom, a small Apple Dock on a side | Rewriting `orientation` and `tilesize` | More user prefs to snapshot and restore; clicking a `.stationary` dock during Mission Control is untested |
| C. Replace (macOS 27+ only) | `.stationary` + shield helper | App's dock only | Private SkyLight SPI + `SetSystemUIMode` helper | Silent breakage in point releases; focus and App Exposé side effects |

Ship A by default, because it keeps Apple's fully functional App Exposé Dock and depends on no private behaviour for correctness. Offer B as an opt-in for users who want their retro dock to stay in Mission Control, and keep C behind an experimental flag until it has been verified on-device across 27.x.

## WindowManager's overlays are the only signal that survives macOS 27

Nothing announces Mission Control. On-device, across Mission Control, App Exposé and Show Desktop, no `NSWorkspace` notification, no distributed notification (observed by name or with a `nil` name) and no Darwin `notify` callback arrived, and the coordinator's separate test likewise saw no distributed or `NSWorkspace` notification on Mission Control entry or exit. The familiar `com.apple.expose.awake`, `com.apple.expose.front.awake` and `com.apple.showdesktop.awake` names are commands sent to the Dock through the private `CoreDockSendNotification` ([Hammerspoon spaces.lua](https://github.com/Hammerspoon/hammerspoon/blob/23e387e2805a9890066366e0ac96c71b27f0cfd5/extensions/spaces/spaces.lua#L244-L272)), and posting them through `DistributedNotificationCenter` "is a no-op" ([docky CGSPrivate.swift](https://github.com/josejuanqm/docky/blob/cb7a6a64483b5cef82b308b6a0958d0df839a779/Docky/Private/CGSPrivate.swift#L188-L194)). `NSWorkspace.activeSpaceDidChangeNotification` covers Space changes only ([Apple](https://developer.apple.com/documentation/appkit/nsworkspace/activespacedidchangenotification)). The Accessibility route died quietly. yabai subscribes to `AXExposeShowAllWindows`, `AXExposeShowFrontWindows`, `AXExposeShowDesktop` and `AXExposeExit` on the Dock for Monterey through Tahoe ([yabai mission_control.c](https://github.com/koekeishiya/yabai/blob/dd845723416f5fe92af49fad5ebab00369e07edd/src/mission_control.c#L52-L106)), but on macOS 27 AltTab found that "the Dock accepts the subscription and posts none of the four, ever", with SkyLight event 1204 "dead the same way" ([AltTab MissionControl.swift](https://github.com/lwouis/alt-tab-macos/blob/c500294bdb01186011a5c64a412b04cef9931bef/src/macos/api-wrappers/MissionControl.swift)). On-device on 27.0.1, all four subscriptions returned success and none ever fired. A 27.2 beta log in [AltTab #6076](https://github.com/lwouis/alt-tab-macos/issues/6076) shows `AXExpose*` names, but those are also the labels AltTab's own window-list classifier logs, so the log does not prove a revival.

What works is reading the gesture's own windows. AltTab recognises WindowManager's overlays "by OWNER, LEVEL and SIZE rather than by name": a screen-sized level-19 shield plus the level-14 Spaces Bar means Mission Control, the shield alone means App Exposé, and a level-18 overlay without a shield means Show Desktop ([AltTab MissionControlOverlay.swift](https://github.com/lwouis/alt-tab-macos/blob/c500294bdb01186011a5c64a412b04cef9931bef/src/macos/api-wrappers/MissionControlOverlay.swift)). On-device the surfaces matched, one per display (`ExposeShieldWindow` at 1512×982 and 2560×1080, `Spaces Bar` at 1512×128 and 2560×96, and a screen-sized `ShowDesktopOverlay`), and none existed at rest. Avoid names in the test: `kCGWindowName` is gated on Screen Recording ([AltTab](https://github.com/lwouis/alt-tab-macos/blob/c500294bdb01186011a5c64a412b04cef9931bef/src/macos/api-wrappers/MissionControlOverlay.swift); [Apple Developer Forums 126860](https://developer.apple.com/forums/thread/126860)), and one developer saw even `kCGWindowOwnerName` come back nil on macOS 26 without that permission, with Apple DTS calling the set of unprotected keys "undocumented and may change at any time" ([Apple Developer Forums 839069](https://developer.apple.com/forums/thread/839069)). Match the owner PID of the WindowManager process instead; `com.apple.WindowManager` is the likely bundle ID, since DockDoor Pro's probe contains that string, but confirm it on-device. Require the shield to be screen-sized, because with Stage Manager on macOS 27 each stage parks a 66×82 `App Icon Window` at level 19 off-screen, which made AltTab think App Exposé was always up, and with Stage Manager on Show Desktop draws no overlay at all ([AltTab #6076](https://github.com/lwouis/alt-tab-macos/issues/6076)). The coordinator's observation that a Dock-owned, display-sized level-20 window comes on screen only during Mission Control gives a second cheap check, but that window also surfaces for bounces and full-screen reveals, and one static on-device snapshot listed it on screen at rest, so use it only to corroborate the shield.

Reads are cheap enough for per-frame work, but not for constant polling.

| Measurement | Cost |
|---|---|
| All on-screen windows (coordinator's test) | ~0.6 ms |
| With `excludeDesktopElements` (coordinator's test) | ~0.17 ms |
| `.optionOnScreenOnly`, 200-read on-device benchmark | 0.216 ms p50, 0.538 ms p95 |
| AltTab's measurement ([AltTab MissionControl.swift](https://github.com/lwouis/alt-tab-macos/blob/c500294bdb01186011a5c64a412b04cef9931bef/src/macos/api-wrappers/MissionControl.swift)) | 0.245 ms p50 |
| `.optionAll` during the Mission Control animation, on-device | 7.8–9.6 ms |
| AltTab's macOS 27 QA, under load | 22–41 ms |

Confirm that the level-14, 18 and 19 overlays survive `excludeDesktopElements` before adopting the cheaper read. A continuous 60 Hz poll would burn roughly 1–4% of a core, too much for an always-on dock, so drive reads from events. The private but permission-free route is SkyLight connection notifications: once `SLSRequestNotificationsForWindows` opts in at least one of the app's own windows (the call replaces rather than appends the list), events 811 (created), 815 (ordered in), 816 (ordered out) and 804 (destroyed) arrive for other processes' windows ([AltTab WindowServerEvents.swift](https://github.com/lwouis/alt-tab-macos/blob/c500294bdb01186011a5c64a412b04cef9931bef/src/events/WindowServerEvents.swift)). On-device, event 811 arrived 6 ms after a Mission Control trigger and an immediate read found the overlays at 18–21 ms; because the shield exists about 17 ms before it is on screen, re-read on the next one or two frames. Without private SPI, a 10 Hz poll costs about 0.2–0.6% of a core, and under policy A a late detection only lengthens the overlap, since the system still removes the panel at 310–338 ms. Exit is the hard edge, because the shield disappears only after the exit animation, 313–334 ms after the toggle-off in all three modes. The fastest public exit signal is the system ordering a `.transient` window back in, which posts `NSWindow.didChangeOcclusionStateNotification` 15–42 ms into the exit; under policy A the dock panel itself is that sentinel.

Space switches are simpler. The public `activeSpaceDidChangeNotification` works everywhere, and SkyLight events 1329 and 1401 (current and active Space changed) arrive in bursts that AltTab debounces into one settled handler ([AltTab WsEventRouting.swift](https://github.com/lwouis/alt-tab-macos/blob/c500294bdb01186011a5c64a412b04cef9931bef/src/windowserver/WsEventRouting.swift#L9-L21)). Full-screen Spaces have no public flag. The private `SLSCopyManagedDisplaySpaces` returns each display's current Space and its `type`, where 4 means full screen ([yabai space.c](https://github.com/koekeishiya/yabai/blob/dd845723416f5fe92af49fad5ebab00369e07edd/src/space.c#L88-L100)), at 0.175 ms per call on-device; the public fallback is Docky's check for another app's layer-0 window matching the screen frame, re-run about 0.85 s later to outlast the exit animation ([docky MainWindow.swift](https://github.com/josejuanqm/docky/blob/cb7a6a64483b5cef82b308b6a0958d0df839a779/Docky/Views/MainWindow/MainWindow.swift#L1176-L1215)). `currentSystemPresentationOptions` describes only the active app, so it misses a full-screen Space on an unfocused display ([Apple](https://developer.apple.com/documentation/appkit/nsapplication/currentsystempresentationoptions)). If the dock offers Mission Control or App Exposé buttons, trigger them with `CoreDockSendNotification`, which on-device worked only once `NSApplication.shared` existed; Mission Control's launch arguments 1 and 2 no longer open Show Desktop or App Exposé on macOS 27 (on-device).

## `.stationary`, not window level, decides whether the dock survives

Level gives no leverage inside Mission Control. On-device, `.stationary` panels at levels 0, 3, 20, 24, 25, 101 and 1000 all stayed visible above the shield, `.transient` panels at 20, 101 and even 1000 (`.screenSaver`) were all hidden, and a level-0 `.stationary` panel drew above the level-19 shield, which suggests Mission Control lifts stationary windows into its own presentation instead of ordering them by level. Apple's wording fits: `.stationary` means "Mission Control doesn't affect the window, so it stays visible and stationary, like the desktop window", while `.transient` "floats in Spaces and hides in Mission Control" and is "the default behavior if windowLevel isn't equal to normal" ([Apple: stationary](https://developer.apple.com/documentation/appkit/nswindow/collectionbehavior-swift.struct/stationary); [Apple: transient](https://developer.apple.com/documentation/appkit/nswindow/collectionbehavior-swift.struct/transient)). Docky's `[.canJoinAllSpaces, .stationary, .ignoresCycle, .fullScreenAuxiliary]` at level 24 stayed visible through Mission Control on-device, and that is precisely the configuration that produces two docks. Do not set `.stationary` and `.transient` together, as DockDoor's gesture HUD does ([DockDoor WindowGestureHUD.swift](https://github.com/ejbills/DockDoor/blob/3044142c907b9cdd49917628847a04970450a8e6/DockDoor/Utilities/Window%20Gestures/WindowGestureHUD.swift#L149)), because the result of that combination is untested.

Level still matters outside Mission Control. On-device `CGWindowLevelForKey` readings place level 20 (`kCGDockWindowLevel`) where Apple's Dock lives, above normal (0) and floating (3) windows, below the menu bar (24), status items (25) and pop-up menus (101), and just above Mission Control's shield (19), the Show Desktop overlay (18) and the Spaces Bar (14). The catch is that the panel shares layer 20 with Apple's Dock, so whenever Apple's Dock escapes outside Mission Control (a full-screen edge push, a bounce), ordering within the layer decides which dock draws on top; Docky's level 24 wins that contest and still loses to WindowManager's hoist inside Mission Control. Full screen is the open question. Apple DTS found that `.floating` and `.statusBar` panels "both sit below full-screen content", while a `.screenSaver` panel with `[.canJoinAllSpaces, .canJoinAllApplications, .fullScreenAuxiliary, .stationary]` stayed on top over full-screen apps on macOS 26 ([Apple Developer Forums 826308](https://origin-devforums.apple.com/forums/thread/826308)), yet Docky ships level 24 with `.fullScreenAuxiliary` and a separate full-screen reveal delay ([docky PR #50](https://github.com/josejuanqm/docky/pull/50)). Test level 20 over a full-screen app and add `.canJoinAllApplications` only if the panel hides there.

For policy A, the panel is a borderless `.nonactivatingPanel` `NSPanel` subclass that never becomes key or main, with `hidesOnDeactivate = false`, in an `.accessory` app, at level 20, with `[.canJoinAllSpaces, .transient, .ignoresCycle, .fullScreenAuxiliary]`. For policies B and C, swap `.transient` for `.stationary` and add a separate tiny `.transient` window purely for its exit-edge occlusion notification. Two behaviours are untested and decide details of the build: whether an alpha-0 or fully clear window still receives occlusion updates (a hidden dock sits at alpha 0), and whether `.canJoinAllSpaces` windows hold still or slide during the Space-switch animation.

```swift
final class DockPanel: NSPanel {
    override var canBecomeKey: Bool { false }
    override var canBecomeMain: Bool { false }
}
let panel = DockPanel(contentRect: dockFrame, styleMask: [.borderless, .nonactivatingPanel],
                      backing: .buffered, defer: false)
panel.level = NSWindow.Level(rawValue: Int(CGWindowLevelForKey(.dockWindow)))   // 20
panel.collectionBehavior = [.canJoinAllSpaces, .transient, .ignoresCycle, .fullScreenAuxiliary]
panel.hidesOnDeactivate = false; panel.isOpaque = false; panel.backgroundColor = .clear
// Earliest public exit signal: the system orders a .transient panel back in 15–42 ms into the exit.
NotificationCenter.default.addObserver(forName: NSWindow.didChangeOcclusionStateNotification,
                                       object: panel, queue: .main) { _ in gestures.reconcile() }

enum Gesture { case none, missionControl, appExpose, showDesktop }
// Owner PID + level + size, never names. wm = PID of com.apple.WindowManager (verify; re-resolve on relaunch).
func classify(windowManagerPID wm: pid_t) -> Gesture {
    let screens = NSScreen.screens.map(\.frame.size)
    let list = CGWindowListCopyWindowInfo([.optionOnScreenOnly], kCGNullWindowID) as? [[String: Any]] ?? []
    var shield = false, spacesBar = false, desktop = false
    for w in list where (w[kCGWindowOwnerPID as String] as? pid_t) == wm {
        let layer = w[kCGWindowLayer as String] as? Int ?? 0
        let b = (w[kCGWindowBounds as String] as? NSDictionary)
            .flatMap { CGRect(dictionaryRepresentation: $0 as CFDictionary) } ?? .zero
        switch layer {
        case 19: shield = shield || screens.contains { b.width >= $0.width && b.height >= $0.height } // skips Stage Manager icons
        case 14: spacesBar = true
        case 18: desktop = true
        default: break
        }
    }
    return shield ? (spacesBar ? .missionControl : .appExpose) : (desktop ? .showDesktop : .none)
}
```

## A fixed window, a 0.2-second slide and fail-visible rules keep auto-hide snappy

Apple's own numbers set expectations. The Dock "only opens if the mouse doesn't move for 0.2 seconds" and its open and close animations "take 0.5 seconds" ([macos-defaults: autohide-delay](https://macos-defaults.com/dock/autohide-delay.html); [macos-defaults: autohide-time-modifier](https://macos-defaults.com/dock/autohide-time-modifier.html)); power users commonly cut the animation to 0.25 ([gist](https://gist.github.com/midudev/aa970a3768665a10e6c8fc5d5c901907)), and Docky defaults its slide to 0.22 s with separate autohide and full-screen reveal delays ([docky PR #50](https://github.com/josejuanqm/docky/pull/50)). Plank keeps hide and unhide delays separate and reveals instantly for non-pointer causes such as drags and open menus ([Plank HideManager.vala](https://raw.githubusercontent.com/ricotz/plank/master/lib/HideManager.vala)). The defaults below are engineering judgement built on those references. One trap deserves mention: do not inherit the user's `autohide-delay` from `com.apple.dock` at runtime, because while parked it reads 100000; read the pre-park snapshot instead.

| Parameter | Default | "Snappy" preset |
|---|---|---|
| Reveal dwell (restart on every pointer move) | 0.12–0.2 s | 0–0.05 s |
| Slide in, ease-out | 0.20–0.25 s | 0.15–0.2 s |
| Slide out, ease-in | 0.18–0.25 s | 0.15–0.2 s |
| Hide grace after the pointer leaves | 0.25–0.4 s | ~0.15 s |
| Reduce Motion replacement | 0.1–0.15 s crossfade, dwell kept | Same |

Animate a layer, not the window. Window-frame animation was reported sluggish and jagged even when view animation inside the same window was smooth, and `setFrame:display:animate:` blocks the main thread ([cocoa-dev](https://lists.apple.com/archives/cocoa-dev/2010/Jul/msg00525.html); [cocoa-dev](https://lists.apple.com/archives/cocoa-dev/2010/Jul/msg00526.html)); that evidence dates from 2010, but nothing newer contradicts it. Keep one fixed panel per display sized for the fully revealed dock plus shadow and magnification headroom, slide a precomposed container's `transform.translation.y`, and on interruption start the new animation from `layer.presentation()` with a duration scaled to the remaining distance. When fully hidden, set opacity 0 and `ignoresMouseEvents = true` rather than leaving a translated edge on screen, which is what produced Docky's "small sliver of the dock" bug ([docky issues](https://github.com/josejuanqm/docky/issues?q=hide)), and avoid `orderOut` on every hide. Use `NSView.displayLink(target:selector:)` (macOS 14+) only to sample the pointer near the edge, pause it elsewhere, and never hide its view, because "If the view is hidden, or not on any display, the callback will not be invoked" ([Apple](https://developer.apple.com/documentation/appkit/nsview/displaylink(target:selector:))).

Mouse-moved and drag events can be watched globally without Accessibility, since only "key-related events" require it, but the global monitor skips the app's own events, so pair it with a local monitor ([Apple: addGlobalMonitorForEvents](https://developer.apple.com/documentation/appkit/nsevent/addglobalmonitorforevents(matching:handler:))). Arm reveal only within the dock's horizontal span plus 8–16 pt, leave 6–10 pt free at each bottom corner so hot corners keep working (hot corners can launch Mission Control or Show Desktop themselves, which the classifier then catches), and make the leave region larger than the enter region to stop flapping at the boundary. Drags and open menus should reveal instantly and block hiding, as in Plank, and Plank's pressure mode (a 60 px threshold, at most 15 px credited per event, reset after 1 s away from the edge) is a good opt-in for users who hate accidental reveals ([Plank HideManager.vala](https://raw.githubusercontent.com/ricotz/plank/master/lib/HideManager.vala)).

**Stacked displays** describe the coordinator's own setup. In a stacked arrangement "The Dock always appears on the very bottom edge of the lower monitor", and the Dock cannot move to a display whose bottom edge fully overlaps another ([Apple Community 256192595](https://discussions.apple.com/thread/256192595)); a dock hidden below the upper display "isn't off-screen at all" but leaks onto the lower one as a strip ([Docky #47](https://github.com/josejuanqm/docky/issues/47)). Recompute on `didChangeScreenParametersNotification` which bottom edges are true edges, arm triggers only there, clip a hidden dock to its own screen, and accept a shield on any display, since each display gets its own. "Displays have separate Spaces" controls whether Apple's Dock can appear on every display ([Apple](https://support.apple.com/guide/mac-help/change-desktop-dock-settings-mchlp1119/27.0/mac/27.0)), but whether its Mission Control reveal lands on one display or all is untested. **The notch** affects only the top edge; use `screen.frame` for the bottom trigger rather than `visibleFrame`, which shifts with Apple's Dock, and never toggle the system Dock's autohide on the fly, which DockDoor found resized windows ([DockDoor v1.3.3](https://newreleases.io/project/github/ejbills/DockDoor/release/v1.3.3)). **Stage Manager**'s strip lives on the left edge, but its level-19 icon windows and missing Show Desktop overlay are exactly why the classifier needs its screen-size filter.

**Around system modes**, suppress pointer reveals while the classifier reports a gesture and until the shield is gone, about 320 ms after the exit begins, because users sweep toward the bottom edge while choosing windows. If the dock was showing before entry, start its fade-in at the exit signal and run it over about 300 ms, so it reaches full opacity as Apple's Dock retreats (that window leaves at 450–597 ms). Afterwards, re-run full-screen and overlap checks, because "`CGWindowList` bounds go stale after a Mission Control / Space transition", and follow the rule Docky's fix states: "Fail-safe direction is "leave the dock visible."" ([docky PR #32](https://github.com/josejuanqm/docky/pull/32)). Refresh any per-app window lists too, since users drag windows between Spaces inside Mission Control and yabai re-syncs after exit for that reason ([yabai event_loop.c](https://github.com/koekeishiya/yabai/blob/dd845723416f5fe92af49fad5ebab00369e07edd/src/event_loop.c#L1528-L1543)). **After wake, unlock, fast user switching or a screen change**, snap to the correct end state without animation, re-resolve the WindowManager PID, and re-subscribe Accessibility observers when the Dock restarts, as yabai does on `NSApplicationDockDidRestartNotification` ([yabai workspace.m](https://github.com/koekeishiya/yabai/blob/dd845723416f5fe92af49fad5ebab00369e07edd/src/workspace.m#L157-L195)); a watchdog that force-hides a dock left shown for 2 s with the pointer far away covers missed exits. **Under Reduce Motion**, read `accessibilityDisplayShouldReduceMotion`, observe `accessibilityDisplayOptionsDidChangeNotification`, and swap the slide for the short crossfade while keeping the dwell ([Apple](https://developer.apple.com/documentation/appkit/nsworkspace/accessibilitydisplayshouldreducemotion)). **To protect the parking itself**, observe the distributed `com.apple.dock.prefchanged` notification that yabai also watches and re-check the parking keys whenever it fires, because any outside change that un-parks the Dock otherwise leaves two docks on screen until the next restart.

## Conclusion

A parked Dock is deferred, not hidden. Every mode the system owns (Mission Control, App Exposé, full-screen edges, attention requests) has its own path back to the screen, and on macOS 27 the most important one belongs to a separate process, WindowManager, that no preference reaches. Designing around ownership instead of suppression changes what detection is for. With a `.transient` panel the system enforces the correct end state even when the app misses a signal, and it supplies the fastest public exit edge for free, so the classifier only shortens a 300 ms overlap rather than guarding correctness. That inversion is what keeps the design robust across releases that keep breaking signals.

Those releases do keep breaking them: macOS 27 silently stopped delivering `AXExpose*`, SkyLight 1204 and Mission Control's launch-argument shortcuts, each without an error. Build the detector to notice its own failure (if the classifier sees an overlay that Accessibility never announced, ignore Accessibility for the session), gate private paths by OS version, and spend a short device pass on macOS 14, 15, 26 and 27 settling the unknowns that decide the remaining choices: whether Apple's parked Dock reveals in Show Desktop or on Space switches, which process owns the overlays before 27, whether `excludeDesktopElements` keeps them, whether an alpha-0 panel still receives occlusion updates, how a level-20 panel behaves over full-screen apps, and whether side-parking holds in Mission Control on every version.
